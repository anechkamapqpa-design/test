# Короткий разбор: как делали

## Порядок работы

1. **Спека до кода.** Сначала я написала [SPEC.md](SPEC.md): стек, схема БД, API, сценарий бота, чек-лист приёмки, порядок этапов.    Спеку я собирала в диалоге с Claude в приложении Cowork. Начала не с кода и не с архитектуры, а с разбора самого ТЗ: что в нём оценивается, что прямо названо неважным, где у меня есть свобода. Из этого вышел приоритет, по которому дальше решались все спорные места: работает   по ссылке важнее полноты функций, полнота важнее качества кода, дизайн не важен вообще,   потому что про него в задании сказано прямо. Стек взяла тот, на котором у меня уже есть   живой продукт: React, Vite, TypeScript, Supabase. На трёхдневном сроке время должно уходить   на задачу, а не на знакомство с инструментами. По каждой развилке Claude предлагал варианты   и аргументы, выбор делала я: один репозиторий вместо двух отдельных сервисов, вебхук вместо   polling, пункт 2 оставить на уровне описания в PRODUCT.md.   Четыре вещи в спеке стоят отдельными запретами, и ровно из-за них она писалась до кода.   Serverless-функция не помнит предыдущий вызов, поэтому состояние диалога бота обязано жить   в базе: иначе бот работает на моей машине и ломается на проде, причём через раз, а не сразу.   Вебхук обязан всегда отвечать телеграму 200, даже когда внутри упало, иначе телеграм   повторяет одно и то же обновление и диалог залипает. Список лидов должен обновляться сам,   потому что проверяющий откроет страницу, напишет боту и будет смотреть на экран, а не жать   F5. И CRM с живыми лидами не остаётся открытой всем по ссылке. Там же требование вести   DECISIONS.md по ходу работы: разбор, написанный потом по памяти, получается про то, что   получилось, а не про то, что решалось.   Дальше ИИ работал строго по ней. Где ему было удобнее по-другому, побеждала спека.
2. **Этапы по SPEC §8, один PR на этап.** Каркас → база и `/api/health` → вебхук-эхо → диалог бота → API и интерфейс → полировка → документы.
   После каждого этапа шла проверка на живом деплое, а не «на глаз в коде». История видна в [PR](https://github.com/anechkamapqpa-design/test/pulls?q=is%3Apr) и коммитах.
3. **Журнал решений по ходу.** [DECISIONS.md](DECISIONS.md) пополнялся в том же коммите, что и код: на каждую развилку три строки — что, варианты, почему.

## Что было интересно

- **Проверка без кода доступа.** ИИ проверял то, что можно проверить без пароля: 401 на всех 8 эндпоинтах, отсутствие секретов в бандле на деплое, вёрстку на 375px. Сценарии под кодом проходила я. В README в чек-листе отмечено, кто что проверял.
- **Не по шаблону.** Для пункта 2 нашёлся путь проще MTProto: Telegram Business позволяет подключить того же бота к личному аккаунту. Описан в [PRODUCT.md](PRODUCT.md) как первый вариант.

## Что бы сделала за ещё одну неделю

1. **Личный Telegram через Telegram Business** (`business_message` в том же вебхуке), затем MTProto-воркер для аккаунтов без Premium.
2. **Склейка дублей** по контакту и `tg_chat_id`: повторное обращение становится событием у существующего лида, а не новым лидом.
3. **Уведомление менеджеру** в Telegram о новом лиде с кнопками «в работу» и «спам».
4. **Карточка лида с историей** из `events` и заметками, ответ клиенту прямо из CRM через бота.
5. **Пользователи** через Supabase Auth вместо общего кода, RLS-политики и автор каждого изменения в `events`.
6. **Автотесты** на диалог бота (это чистая функция «шаг + сообщение → шаг + ответ») и смоук-тест API в CI.
