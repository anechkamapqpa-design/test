Техническое задание для Claude Code. Работай строго по этому файлу. Если что-то в нём
противоречит твоему привычному способу, выбирай этот файл. Если встретишь настоящую

## 0. Контекст и цель

Агентство получает заявки из разных мест и теряет их в переписке. Нужна простая CRM, в которую
лиды попадают сами, и в которой их можно разметить тегами и быстро найти.

Это тестовое задание с жёстким сроком. Критерий успеха один: **по живой ссылке открывается
работающая вещь**, в которой проходится полный путь от сообщения в телеграм-боте до лида
с тегом в CRM. Красота кода и дизайн не оцениваются. Работоспособность оценивается.

Приоритет при любом конфликте: **работает по ссылке > полнота функций > качество кода > дизайн**.

## 1. Стек, зафиксирован

Не меняй без вопроса.

- Один репозиторий, один деплой на **Vercel**.
- Фронтенд: **Vite + React 18 + TypeScript + Tailwind CSS**. SPA, одна страница.
- Бэкенд: **serverless-функции Vercel** в папке `/api`, TypeScript, Node 20.
- База: **Supabase Postgres**. Обращение к базе только из функций `/api`, через
  `@supabase/supabase-js` с service role ключом.
- Телеграм: **Bot API через вебхук**, без polling. Библиотеки для ботов не нужны,
  работай с HTTP напрямую через `fetch`.

### Жёсткие запреты

- Service role ключ Supabase **никогда** не попадает в браузерный код. Только в `/api`.
- Никакого `VITE_SUPABASE_SERVICE_ROLE_KEY`. Любая переменная с префиксом `VITE_`
  попадает в бандл и видна всем.
- Никакого polling телеграма: на serverless он не работает.
- Никакого хранения состояния диалога в памяти процесса: функции не помнят предыдущий вызов.
  Состояние только в базе.
- Не подключай ORM, не подключай state-менеджер, не подключай UI-библиотеку компонентов.
  `fetch` и `useState` достаточно.

## 2. Схема данных

Создай файл `supabase/migrations/001_init.sql` ровно с таким содержимым и примени его
через SQL Editor в Supabase (я применю руками, ты только подготовь файл и скажи мне).

```sql
create extension if not exists "pgcrypto";

create table leads (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  contact     text not null,
  request     text,
  source      text not null check (source in ('bot','manual','telegram_personal')),
  status      text not null default 'new' check (status in ('new','in_progress','done','rejected')),
  tg_chat_id  bigint,
  tg_username text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

create table tags (
  id    uuid primary key default gen_random_uuid(),
  name  text not null unique,
  color text not null default 'slate'
);

create table lead_tags (
  lead_id uuid not null references leads(id) on delete cascade,
  tag_id  uuid not null references tags(id)  on delete cascade,
  primary key (lead_id, tag_id)
);

create table bot_sessions (
  chat_id    bigint primary key,
  step       text not null,
  draft      jsonb not null default '{}'::jsonb,
  updated_at timestamptz not null default now()
);

create table events (
  id         bigserial primary key,
  lead_id    uuid references leads(id) on delete cascade,
  kind       text not null,
  payload    jsonb,
  created_at timestamptz not null default now()
);

create index leads_created_at_idx on leads (created_at desc);
create index lead_tags_tag_idx    on lead_tags (tag_id);

alter table leads        enable row level security;
alter table tags         enable row level security;
alter table lead_tags    enable row level security;
alter table bot_sessions enable row level security;
alter table events       enable row level security;

insert into tags (name, color) values
  ('горячий','red'), ('перезвонить','amber'), ('бюджет','emerald'), ('спам','slate');
```

RLS включена, политик нет сознательно: с анонимным ключом база закрыта полностью,
весь доступ идёт через service role из `/api`. Напиши это в README одной строкой,
чтобы было видно, что это решение, а не недоработка.

Таблица `events` нужна для одной цели: по каждому лиду видно, откуда он пришёл и что
с ним происходило. Пиши туда событие при создании лида, при смене статуса и при изменении тегов.

## 4. API

Все эндпоинты возвращают JSON. Ошибки в формате `{ "error": "текст" }` с корректным кодом.
Везде, кроме вебхука и `/api/health`, требуй заголовок `x-app-key` и сверяй с `APP_ACCESS_KEY`.
Без него возвращай `401`.

| Метод  | Путь                        | Что делает |
|--------|-----------------------------|------------|
| GET    | `/api/health`               | `{ok:true, db:true}`, проверяет соединение с базой |
| POST   | `/api/telegram`             | вебхук телеграма, см. раздел 5 |
| GET    | `/api/leads`                | список лидов, фильтры `?tag=<id>&status=<status>&q=<строка>` |
| POST   | `/api/leads`               | создать лида руками: `{name, contact, request}`, `source='manual'` |
| PATCH  | `/api/leads/[id]`           | изменить `status`, `name`, `contact`, `request` |
| DELETE | `/api/leads/[id]`           | удалить лида |
| GET    | `/api/tags`                 | список тегов с количеством лидов по каждому |
| POST   | `/api/tags`                 | создать тег: `{name, color}` |
| POST   | `/api/leads/[id]/tags`      | навесить тег: `{tagId}` |
| DELETE | `/api/leads/[id]/tags`      | снять тег: `{tagId}` |

`GET /api/leads` возвращает лида вместе с его тегами, одним запросом, без доборов на клиенте:

```json
[{ "id":"...", "name":"Иван", "contact":"@ivan", "request":"нужен лендинг",
   "source":"bot", "status":"new", "created_at":"...",
   "tags":[{"id":"...","name":"горячий","color":"red"}] }]
```

Фильтр `q` ищет по `name`, `contact` и `request`, регистр не важен.

## 5. Телеграм-бот

### Общая механика

Вебхук `POST /api/telegram`. Первым делом сверяй заголовок
`X-Telegram-Bot-Api-Secret-Token` с `TELEGRAM_WEBHOOK_SECRET`. Не совпал, возвращай `401` и выходи.

**Всегда отвечай телеграму `200`**, даже если внутри что-то упало, иначе телеграм будет
повторять одно и то же обновление и диалог залипнет. Ошибку логируй и пиши пользователю
понятное сообщение.

Состояние диалога живёт в `bot_sessions`: `step` и `draft`. Шаги:

```
idle -> ask_name -> ask_contact -> ask_request -> done
```

### Сценарий

| Шаг | Что бот пишет | Что делает с ответом |
|-----|---------------|----------------------|
| `/start` | «Привет! Оставьте заявку, это три вопроса. Как к вам обращаться?» | `step=ask_name` |
| `ask_name` | «Как с вами связаться? Телефон, почта или телеграм.» | пишет `draft.name`, `step=ask_contact` |
| `ask_contact` | «Коротко опишите задачу.» | пишет `draft.contact`, `step=ask_request` |
| `ask_request` | «Готово, заявка принята. Мы свяжемся с вами.» | создаёт лида, `step=idle`, `draft={}` |

- `/cancel` в любой момент: «Отменила. Напишите /start, когда будете готовы», `step=idle`, `draft={}`.
- Любое сообщение при `step=idle` и без команды: «Чтобы оставить заявку, напишите /start».
- Пустое или не текстовое сообщение (фото, стикер, голосовое): «Пришлите, пожалуйста, текстом».
- Контакт проверяй мягко: подходит, если похоже на телефон, почту или `@username`.
  Не похоже, один раз переспроси: «Не разобрала контакт. Пришлите телефон, почту или @ник»,
  со второй попытки принимай как есть. Жёсткая валидация в заявке вредит конверсии,
  задача бота собрать контакт, а не отфильтровать человека.
- Длину каждого ответа ограничь 500 символами, обрезай с многоточием.

При создании лида заполняй `source='bot'`, `tg_chat_id`, `tg_username` и пиши событие
в `events` с `kind='lead_created'` и payload с исходными сообщениями.

### Установка вебхука

Положи в README готовую команду, с подстановкой домена:

```bash
curl -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -d "url=https://<домен>.vercel.app/api/telegram" \
  -d "secret_token=$TELEGRAM_WEBHOOK_SECRET"
```

И команду проверки: `curl "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getWebhookInfo"`.
В README напиши, что в ответе надо смотреть на `last_error_message`: это первое место,
куда стоит смотреть, если бот молчит.

## 6. Интерфейс

Одна страница, работает на телефоне и на ноутбуке. Tailwind, без библиотеки компонентов.
Дизайн не оценивается, поэтому делай аккуратно и быстро: читаемый шрифт, нормальные отступы,
ничего не вылезает за экран.

**Вход.** При первом открытии показывай поле «Код доступа». Введённый код храни в
`localStorage` и отправляй в заголовке `x-app-key`. Неверный код, покажи сообщение об ошибке.
Это одна форма и десяток строк, полноценную авторизацию не делай.

**Экран, сверху вниз:**

1. Заголовок и счётчики: всего лидов, новых, за сегодня.
2. Строка фильтров: поиск, чипы тегов (нажатие фильтрует, повторное снимает), селект статуса,
   кнопка «Сбросить».
3. Кнопка «Добавить лида», открывает панель с формой: имя, контакт, запрос. Имя и контакт
   обязательны. После отправки список обновляется, панель закрывается.
4. Список лидов, новые сверху. В карточке лида: имя, контакт, запрос, бейдж источника
   (бот, вручную, личный телеграм), селект статуса, чипы тегов с крестиком и кнопка
   «+ тег» со списком существующих тегов и возможностью создать новый.

**Поведение, которое обязательно работает:**

- Смена статуса и правка тегов сохраняются сразу, без кнопки «Сохранить».
- После любого изменения список остаётся на том же фильтре.
- Пока запрос идёт, кнопка заблокирована. Если запрос упал, покажи видимое сообщение об ошибке,
  а не тихое ничего.
- Пустой список и пустой результат фильтра показывают разный текст.
- Автообновление списка раз в 15 секунд, чтобы лид из бота появлялся без перезагрузки.
  Это важно для демонстрации: проверяющий напишет боту и будет смотреть на открытую страницу.

## 7. Чего сознательно не делаем

Напиши это в README отдельным разделом, формулировками из списка.

- Пункт 2 задания, подключение личного телеграма как источника лидов, **не реализуем кодом**.
  Задание это разрешает. В схеме данных место под него уже есть: `source='telegram_personal'`.

- Роли и права, несколько пользователей, аудит доступа.
- Уведомления, воронка, аналитика, экспорт.
- Дедупликация лидов: один человек, написавший дважды, создаёт двух лидов. Решение осознанное,
  в продукте это закрывается склейкой по контакту.
- Тесты. На трёхдневном сроке вместо тестов делаем ручной чек-лист из раздела 9.

## 11. Если что-то не работает

Прежде чем переписывать код, посмотри в этом порядке:

1. Бот молчит: `getWebhookInfo`, поле `last_error_message`.
2. Ошибка 500 в функции: логи деплоя в Vercel, вкладка Functions.
3. База не отвечает: проверь, что `SUPABASE_URL` и ключ заданы **в переменных окружения
   Vercel**, а не только в локальном `.env`, и что после их добавления был новый деплой.
4. Данные не отдаются: RLS включена, значит запрос идёт не с service role ключом.
5. Фронтенд получает 401: заголовок `x-app-key` не доехал.
