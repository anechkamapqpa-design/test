# DECISIONS

Журнал развилок. Каждая запись: что решала, какие были варианты, почему этот.

## 1. Tailwind: v4 через плагин Vite
- **Что:** как подключить Tailwind к Vite.
- **Варианты:** v3 с `tailwind.config.js` + PostCSS; v4 с `@tailwindcss/vite`.
- **Почему v4:** одна строка `@import "tailwindcss"` и плагин, без двух конфигов. Меньше мест, где можно ошибиться на сжатом сроке.

## 2. Один деплой на Vercel, SPA-rewrite кроме /api
- **Что:** как отдавать фронт и API с одного домена.
- **Варианты:** отдельный бэкенд (Render/Railway) + статика; всё на Vercel.
- **Почему Vercel:** один репозиторий, одна ссылка, нет CORS. `vercel.json` переписывает всё, кроме `/api/`, на `index.html`.

## 3. Service role ключ только на сервере
- **Что:** как фронт получает данные из Supabase.
- **Варианты:** supabase-js в браузере с anon-ключом и RLS-политиками; все запросы через `/api` с service role.
- **Почему `/api`:** service role обходит RLS, в бандле он равен открытой базе. Держим его в `api/_lib/db.ts`, без префикса `VITE_`, фронт ходит только в `/api`.

## 4. RLS включена, политик нет
- **Что:** как закрыть таблицы от прямого доступа.
- **Варианты:** выключить RLS; написать политики под anon/authenticated; включить RLS без политик.
- **Почему без политик:** с anon-ключом база закрыта полностью, и это то, что нужно. Единственный путь к данным идёт через service role в `/api`. Политики понадобятся, когда появятся пользователи и роли, сейчас их нет.

## 5. /api/health проверяет базу реальным запросом
- **Что:** чем доказывать `db:true`.
- **Варианты:** просто проверить, что заданы переменные; сделать запрос.
- **Почему запрос:** `count` по `tags` с `head:true` ловит и неверный ключ, и непримененную миграцию. Переменные могут быть заданы, а база при этом недоступна.

## 6. Вебхук, а не polling
- **Что:** как получать сообщения боту.
- **Варианты:** long polling `getUpdates`; вебхук `setWebhook`.
- **Почему вебхук:** на Vercel нет постоянно живого процесса, функция живёт секунды и только пока есть запрос. Polling там некому крутить. Вебхук сам будит функцию на каждое сообщение.

## 7. Вебхук всегда отвечает 200 (кроме чужого секрета)
- **Что:** что возвращать телеграму, если внутри упало.
- **Варианты:** честный 500; всегда 200 и лог.
- **Почему 200:** на не-2xx телеграм повторяет то же обновление, и диалог залипает на одной ошибке. Ошибку пишем в лог Vercel, пользователю отвечаем понятным текстом. 401 только на неверный `X-Telegram-Bot-Api-Secret-Token`: это не телеграм, повторять нечего.

## 8. Состояние диалога в базе, а не в памяти
- **Что:** где помнить, на каком вопросе человек.
- **Варианты:** `Map` в памяти функции; таблица `bot_sessions` (`step` + `draft`).
- **Почему база:** каждый вызов на Vercel может попасть в новый инстанс, память между сообщениями не переживает. `bot_sessions` по `chat_id` переживает холодный старт и редеплой посреди диалога.

## 9. Мягкая валидация контакта
- **Что:** что делать, если контакт не похож на телефон, почту или @ник.
- **Варианты:** не проверять; требовать до победного; переспросить один раз.
- **Почему один раз:** опечатку ловим, а человека не теряем. Задача бота собрать контакт, а не отсеять. Флаг `contactRetried` лежит в `draft`. Проверка ищет контакт внутри фразы («пишите на ivan@mail.ru» тоже подходит).

## 10. Если лид не записался, шаг не сбрасываем
- **Что:** что делать при ошибке базы на последнем шаге.
- **Варианты:** сбросить диалог; оставить `ask_request`.
- **Почему оставить:** человек просто пришлёт описание ещё раз, и лид создастся. Имя и контакт заново спрашивать не надо.

## 11. Фильтр по тегу двумя запросами на сервере
- **Что:** как отдать лидов с тегом X и при этом все их теги.
- **Варианты:** `lead_tags!inner` (фильтрует и сами теги, у лида останется только X); RPC/вьюха в базе; сначала id лидов по тегу, потом основной запрос с `.in('id', ...)`.
- **Почему два запроса:** оба на сервере, клиент получает готовый ответ одним вызовом, как требует SPEC. Без новых объектов в базе.

## 12. Код доступа сверяется timingSafeEqual
- **Что:** как сравнивать `x-app-key`.
- **Варианты:** `===`; `timingSafeEqual`.
- **Почему:** одна строка, а по времени ответа код не подобрать. Полноценную авторизацию сознательно не делаем.

## 13. После любой правки перечитываем список, а не правим его локально
- **Что:** как обновить экран после смены статуса или тега.
- **Варианты:** подменить лида в массиве ответом API; заново запросить список с текущим фильтром.
- **Почему перечитать:** если сняли тег, по которому стоит фильтр, лид должен уйти из выдачи. Повторный запрос с тем же фильтром даёт правильный ответ без отдельной логики на клиенте. Счётчики тегов обновляются заодно.

## 14. Новый тег создаётся прямо из карточки и сразу вешается
- **Что:** где создавать теги.
- **Варианты:** отдельный экран тегов; поле «новый тег» в выпадашке «+ тег».
- **Почему из карточки:** тег придумывают, глядя на конкретного лида. Название приводим к нижнему регистру, дубль даёт 409 «Такой тег уже есть».

## 15. Автообновление раз в 15 секунд, а не realtime
- **Что:** как лид из бота появляется на открытой странице.
- **Варианты:** Supabase Realtime (нужен anon-ключ в браузере и RLS-политики); SSE/WebSocket (на serverless не держится); `setInterval` на 15 с.
- **Почему интервал:** база остаётся закрытой (см. 3–4), кода десять строк. Пока вкладка скрыта, не опрашиваем. Задержку до 15 секунд на демо видно, но она не мешает.

## 16. Счётчики считаются по всем лидам, а не по фильтру
- **Что:** что показывают «всего / новых / за сегодня».
- **Варианты:** по текущей выдаче; по всей базе.
- **Почему по всей:** это сводка над фильтрами. При активном фильтре делаем второй запрос без фильтра. «Сегодня» считаем в часовом поясе браузера.

## 17. Код доступа не кладём в публичный README
- **Что:** SPEC просит указать код доступа в README.
- **Варианты:** записать в README; передать вместе со ссылкой в сообщении со сдачей.
- **Почему в сообщении:** репозиторий публичный, а код открывает всю базу лидов с контактами людей. Проверяющим он нужен так же, но в индекс поисковиков не попадёт.

## 18. Для личного Telegram сначала Telegram Business, потом MTProto
- **Что:** как закрыть пункт 2 задания в продукте.
- **Варианты:** MTProto userbot (GramJS/Telethon); Telegram Business с подключённым ботом.
- **Почему Business первым:** апдейты `business_message` приходят на уже существующий вебхук, сессию аккаунта хранить не нужно, риска бана за автоматизацию нет. MTProto остаётся для аккаунтов без Premium.
